# 项目定位与展示方案讨论记录

> 日期：2026-08-30 ｜ 状态：讨论结论 ｜ 适用版本：远程 `main`（B4 已合并）

## 1. 当前项目实际形态

当前已实现的核心业务能力是：

```text
音频上传 → 文件校验 → 创建异步任务 → 转录 → 摘要 → 查询结果 → 下载转录
```

同时提供天气工具调用：

```text
地点请求 → WeatherProvider → wttr.in → 标准化天气结果
```

项目当前主要是 TypeScript/Node.js/Express HTTP 服务，尚未开发 Web 前端，因此实际操作方式仍是终端或其他 HTTP 客户端调用 API。当前更准确的定位是“全栈项目中的后端核心与 API 基础”，而不是已经完成的面向普通用户的完整博客产品。

## 2. 为什么后端设计较复杂

复杂度主要来自可靠运行异步 AI 服务的工程要求，而不是单纯增加模块：

- 转录和摘要耗时较长，需要异步 Job、队列和 Worker，避免阻塞 HTTP 请求。
- OpenAI、天气等外部服务可能超时或失败，需要超时、重试和稳定错误码。
- 服务重启可能中断任务，需要持久化、恢复和 `PROCESS_INTERRUPTED` 语义。
- 重复上传可能造成重复计费，需要 `Idempotency-Key` 和并发安全的幂等占位。
- 音频上传涉及 MIME、魔数、大小、时长、临时文件和路径安全。
- 适配器和端口隔离模型、天气及文件实现，便于替换外部服务和后续扩展。
- OpenAPI、requestId、结构化日志、测试和 CI 用于验证行为而非只展示成功路径。

## 3. 设计与实际的阶段性不匹配

这种不匹配确实存在，但属于“工程基础先于产品界面”的阶段性问题：

1. 后端架构已经支持可部署、可测试的服务，但用户界面尚未实现。
2. 任务清单中的 metrics、Grafana、安全扫描、制品治理、完整 E2E 等部分长期维护能力，超出了当前单机演示的最低需求。
3. 核心业务、质量治理和长期增强如果混在一条主线，会让项目显得比实际产品范围更重。

因此不应把尚未实现的前端、CMS 发布、SEO/GEO、品牌知识库、多人协作或多租户能力描述为当前功能，也不应为了完成清单而提前固化全部长期增强任务。

## 4. 当前版本与后续范围

### 当前已完成

- 音频上传、校验、异步转录、摘要、查询和转录下载
- 天气接口及成功/无效地点/超时错误处理
- Job 状态机、文件持久化、恢复、幂等、重试/超时和基础错误边界
- OpenAPI 契约、结构化日志、测试、覆盖率和 CI 基础门禁

### 答辩前优先

- 设计不依赖现场 Node、密钥和网络的展示方案
- 用录屏、PPT storyboard、截图和离线材料展示核心闭环
- 根据展示场景反推必要的质量、安全和证据要求
- 完成对答辩必需的 DTO/契约测试、必要防护和核心集成测试

### 后续按需决定

- 最小 Web 前端：上传、进度、摘要预览、转录下载
- 文章编辑、Markdown/HTML 导出和 CMS 发布
- 本地 Whisper、其他模型平台、更多外部工具
- 健康检查、metrics、Prometheus/Grafana、安全扫描、深度 E2E 和运维治理

后续任务遵循 YAGNI：先由答辩方案、实际部署方式和剩余时间确定需求，再将确有必要的增强能力转化为正式任务。

## 5. 答辩中的准确表述

推荐表述：

> 当前版本先完成了多模态博客素材服务的后端核心：音频经过异步转录和摘要后可查询、可下载，并通过天气工具调用展示外部能力编排。终端/API 是当前的验证载体，Web 前端属于后续产品化方向。项目的创新重点是可靠的异步工作流、可审计状态机、适配器隔离和可验证的工程实现，而不是声称已经具备商业博客平台的全部功能。

避免表述：

- “已经是完整的全栈博客产品”
- “全面替代 Jasper、Notion、HubSpot 等商业平台”
- “市场上唯一的音频博客助手”
- “所有质量、监控和长期运维能力都已完成”

## 6. OpenAI SDK 与 Responses API 选型讨论

### 6.1 为什么当前选择 OpenAI

这不是对其他 AI 厂商的绝对否定，而是基于本项目当前约束的工程决策：

- 原始教材和已有实现已经基于 OpenAI，能够复用音频转录、摘要和工具调用经验。
- 项目同时需要音频转录、文本摘要、函数/工具调用，并预留文件、图像和更多工具扩展能力。
- 当前使用的 `openai-hk` 网关主要提供 OpenAI 兼容接口，Responses API 是已验证的兼容路径。
- 官方提供 TypeScript/JavaScript SDK，与项目的 Node.js 技术栈和 ESM 模块体系匹配。
- OpenAI 依赖被 `Transcriber`、`Summarizer` 等端口和基础设施适配器隔离，未来可替换其他厂商或本地模型，不要求重写领域层。

因此应表述为：当前选型是为了匹配已有基础、所需能力、网关环境和迁移成本，同时保留替换边界。

### 6.2 为什么使用 Responses API

项目早期教材使用 Assistants API，但该接口已弃用并关闭；项目通过 ADR-0001 统一迁移到 Responses API。当前摘要和天气工具编排采用：

```text
responses.create
  → function_call
  → 本地执行 WeatherProvider
  → previous_response_id + function_call_output
  → 最终结果
```

选择 Responses API 的理由：

- 更适合统一处理文本、文件、图像、工具和流式输出等输入/输出形态。
- 工具调用的响应、调用标识和后续结果结构更适合本项目的多轮工作流。
- 可直接延续已完成并验证过的迁移模式，避免重新设计 Chat 消息历史和工具消息协议。
- 为后续 Agent 或更多外部工具扩展保留更自然的接口边界。

Chat Completions 仍适用于简单的无状态文本对话或由应用自行维护消息历史的场景；它“更常见”并不意味着更适合本项目。Responses API 也不承担所有 AI 任务：音频转录仍通过专用音频转录接口完成，Responses API 主要负责摘要和工具编排。

### 6.3 与其他 AI 平台的比较边界

市场产品和其他模型平台可能采用 Python、TypeScript/Node.js、Go、Java 或多语言微服务，商业产品通常不会公开完整后端技术栈。因此不能宣称市场产品都使用或都不使用本项目的技术栈。

本项目的可辩护差异不在于“选了某一家 SDK”，而在于：

- 音频优先的博客素材闭环；
- 显式 Job 状态机、幂等、恢复、重试和稳定错误边界；
- OpenAI 与天气服务通过适配器隔离；
- OpenAPI、结构化日志、测试和 CI 带来的工程透明度。

若未来更换或增加其他模型供应商，应重新评估音频能力、工具调用协议、流式/多轮状态、SDK 成熟度、网关兼容性、成本和数据策略；不能把供应商切换简化为只修改一个配置项。

### 6.4 答辩推荐表述

> 本项目选择 OpenAI，是因为它与已有教材基础、音频转录和工具调用需求以及当前网关环境匹配；同时通过端口和适配器隔离供应商依赖。由于教材使用的 Assistants API 已弃用并关闭，项目统一迁移到 Responses API。相比简单的 Chat Completions，Responses API 更适合本项目的多模态输入、工具调用和可扩展工作流。音频转录仍使用专用接口，Responses API 主要负责摘要和工具编排。

应避免宣称 OpenAI 或 Responses API 在所有场景都绝对优于其他方案，也不应把更换供应商描述为零成本操作。

## 7. AI 博客助手能力边界

当前“AI”主要体现为两项已实现能力：

- 使用 OpenAI 音频转录模型，把采访、讲座或口述音频转换为文本。
- 使用语言模型对转录文本进行中文要点式生成摘要，通常输出类似 Markdown 的 `- 要点` 列表。

天气接口体现的是“模型/应用调用外部工具”的扩展能力。它返回标准化天气 DTO，不是模型凭记忆生成天气信息。

当前摘要属于通用生成式摘要：模型会重新组织和压缩转录内容，不保证逐句摘录，也尚未输出固定的标题、关键词、文章大纲、行动项或 SEO 元数据。摘要以字符串形式返回并保存为 `summary.txt`，因此当前项目更准确的定位是“AI 博客素材助手”，而不是已经具备完整文章自动生成和发布能力的博客平台。

答辩推荐表述：

> 系统将音频素材自动转录，再由语言模型提炼为中文要点摘要，形成可查询、可下载的博客素材；天气工具调用用于展示外部数据编排。完整文章生成、编辑、SEO 优化和 CMS 发布属于后续产品化方向。
